# v0.5 implementation and review

The v0.5 Case workspace implements Overview, Brief, Affidavits, Exhibits,
Stipulations, and Rules. Data is supplied through `CaseRepository` and
`CaseBriefService`, with injectable in-memory mocks. Brief facts have typed source
references and explanations; opening a reference displays the matching exhibit
description or affidavit, and closing it returns to the brief. The brief has
independent loading, empty, failure, and retry states so a service failure does
not hide the case materials.

The existing 14 exhibit descriptions and six witnesses are preserved. The six
affidavits, three stipulations, four timing rules, and brief are newly authored,
fictional demo material. No original competition packet or exhibit files exist
in this repository. The interface labels the sample packet and sample AI brief.
Exhibit links therefore display the repository's descriptions, rather than PDFs
or images that are not available.

## Findings recorded without fixes

These are observations about existing behavior or future requirements. They
have not been addressed by this feature implementation.

1. **Assigning a role would lower the current readiness metric.**
   `lib/state/task_controller.dart` defines readiness as completed tasks divided
   by all tasks. The v0.7 plan says assigning responsibilities both creates tasks
   and raises readiness. With the demo's five completed tasks out of 12, adding
   three unfinished responsibilities changes readiness from 42% to 33%. The
   planned expectation and the existing metric need a product decision.

2. **Repository failures leave the app without a recovery path.**
   `lib/app.dart` starts the controllers' asynchronous `load()` calls without
   handling failures. The case, team, and task repository load methods do not
   expose errors. `lib/features/home/home_page.dart` shows an empty body until
   all three controllers load. A failed repository request can therefore leave
   Home blank, with no error or retry action; the new Case tab's initial loading
   indicator likewise cannot report a repository failure. Brief-service failure
   is handled separately as part of the new feature. General repository error
   handling is already scheduled for v1.0.

3. **The trial countdown resets on every launch.**
   `SeedData.harmon` sets the trial to today plus 23 days and task due dates
   relative to today. Reloading regenerates those dates, so a student never sees
   the demo trial draw closer across launches. This is deliberate in the seed
   comment, but the Home presentation does not explain that behavior.

4. **Date-sensitive labels can remain stale while the app stays open.**
   Home reads the greeting and due/countdown labels during a rebuild. There is
   no clock-driven notification at midnight or greeting boundaries. An idle app
   can continue showing yesterday's countdown or an earlier greeting until
   another rebuild occurs. Relevant files: `home_page.dart`, `session_controller.dart`,
   and `core/clock.dart`.

5. **“Ask the case” currently ends at a placeholder.**
   Home invites the user to ask about facts and arguments, but the destination
   `lib/features/research/research_page.dart` contains only “Coming in v0.6.”
   This is a planned milestone gap, but it is currently a dead end for a user
   following the prominent Home action.

6. **The planned script warning could miss a team time overrun.**
   v0.9 describes comparing one witness script's estimate with the matching
   timing rule. The direct and cross limits in v0.5 are totals per side across
   witnesses. Three 10-minute direct scripts each fit under a 25-minute limit,
   while their combined 30 minutes exceed it. The plan does not yet specify
   aggregation or allocation of that shared budget.

7. **Fresh installs are not pinned to the same dependency versions.**
   `.gitignore` ignores every `*.lock`, including `pubspec.lock`, and
   `pubspec.yaml` uses version ranges. Different fresh clones can resolve
   different dependencies even with the same Flutter version. The local SDK
   used for validation is Flutter 3.47.2 / Dart 3.13.2; CI and the plan name
   Flutter 3.47.6. No SDK or dependency version changes were made.

8. **Project documentation and release metadata lag behind the code.**
   README still describes a new Flutter template; the plan's starting-point
   paragraph still describes the counter demo; `pubspec.yaml` still declares
   `0.1.0+1`. No existing v0.x Git tags were present when the repository was
   cloned, despite the per-iteration tagging checklist. These can confuse a
   developer trying to identify the implemented release.

## Manual developer check

Automated validation passed locally: `flutter analyze --no-pub` (no issues),
`flutter test --no-pub` (68 tests), and `flutter build web --no-pub` (production
bundle generated at `build/web`). The new widget tests cover every brief evidence
link and all six sections at 390×844 with 1.3× text in Light, Dark, and Midnight.

The repository's `.cursor/rules/no-agent-ui-testing.mdc` reserves browser smoke
tests for developers. From the project directory, run `flutter run -d chrome`
and use a 390×844 browser viewport.

1. Open Case and switch through all six section chips. Confirm the header shows
   14 exhibits, six witnesses, and six affidavits.
2. In Brief, open an exhibit reference and an affidavit reference. Read each
   source, close it, and confirm you remain at the same place in Brief.
3. Read the anticipated arguments and counters, then check the six affidavits,
   14 exhibits, and three stipulations in their sections.
4. Open Rules: confirm 5-minute opening, 25-minute direct total, 20-minute cross
   total, and 9-minute closing, each per side. Switch tabs and back to confirm
   your Case selection is retained.
5. In Me → Design system and themes, try Dark and Midnight, then return to Case.
   Repeat section and source checks with browser text enlarged.

The iteration's manual smoke test and release tag remain pending that review.
